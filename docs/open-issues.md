# Undecided matters

This page lists details that the [format specification](config-format.md) does not settle. References to established rules identify what is already fixed; they do not reopen those decisions. The [type profile page](type-profile.md) separates the candidate catalogue from the established byte representation.

[Back to the documentation](README.md)

| Item | Undecided details |
|-------------|--------------------------------------------------------------------|
| Future versions, properties and file extension | Future version numbering and compatibility policy, additional properties and dedicated file extension. The mandatory declaration region, blank separator and exact current declaration `@dotReg 1` are established in [section 1.1](config-format.md#11-file-property-declarations) |
| Type names | Which [candidate names](type-profile.md#candidate-type-names-and-sample-values) become standard permitted names, aliases and case sensitivity |
| Remaining details of type expression grammar | Empty type expressions and the concrete grammar for quotes and escapes within type expressions. The prohibition on internal whitespace, and the decision not to prohibit symbols and nested parentheses for compound types outright, are established in [section 6.1](config-format.md#61-position-and-omission). The type conversion layer defines the meaning and validity of each type expression |
| Remaining whitespace rules for type annotations | Alignment tabs between the key and the type expression, or between the closing parenthesis and the colon. The established alignment rules are in [section 6.2](config-format.md#62-whitespace-for-alignment) |
| Future escape extensions | Whether to add forms beyond the basic notation, `\u{H...}` and `\uXXXX` defined in [section 3.4](config-format.md#34-common-escapes-within-quotes). The Unicode scalar value range, surrogate pairs in the four-digit form, rejection of invalid notation and absence of replacement are established |
| Unicode character classification | The concrete classification of whitespace and control characters in unquoted key elements. The absence of Unicode normalisation, and the principle that quoted key elements allow any valid UTF-8 string, are established in [section 3](config-format.md#3-key-paths) |
| Remaining details of value quoting | Categories and notification points for decoding errors. First-character selection between wholly quoted and literal single-line values, preservation of later literal quotes and backslashes, triple-quoted markers and margins, literal pipe detection, form-specific whitespace and escape handling, and explicit empty block state are established in [section 8.2](config-format.md#82-double-quoted-values-and-common-string-decoding), [section 8.3](config-format.md#83-triple-quoted-multiline-values) and [section 8.4](config-format.md#84-literal-pipe-blocks) |
| Type-specific decoders | Concrete meaning and conversion for numbers, booleans, lists and other types, and accepted spellings for address and time values. The [`bytes` text representation as standard Base64](type-profile.md#established-bytes-representation) is established. Common string decoding, empty-header detection including pipe blocks, explicit empty block values and the equivalence of unset to an empty string when string retrieval is permitted are established in [section 8](config-format.md#8-preserving-right-hand-sides-and-interpreting-values) |
| Type-specific interpretation of unset | Treatment in non-string types and the relationship to required fields and defaults. The established conversion and retrieval procedure is in [section 8.1](config-format.md#81-type-conversion-and-retrieval) |
| Type expression identity | Matching of type aliases, alternative spellings, compound types and similar expressions. The established mismatch behaviour is in [section 8.1](config-format.md#81-type-conversion-and-retrieval) |
| Failure of conversion to a declared type | Error categories and notification points when conversion to the specified type expression is impossible. No fallback to another type expression or a string is permitted under [section 8.1](config-format.md#81-type-conversion-and-retrieval) |
| Relationship to schemas | Connecting configuration schemas to declarations and retrieval requests, and handling unknown type names. Established responsibility boundaries are in [section 11](config-format.md#11-responsibilities-of-syntax-processing-and-consuming-applications) |
| APIs and value retention | Output representation and canonical notation for key paths that preserve element boundaries; output representation for type expressions; single, collection and indexed retrieval APIs, including aggregate handling of mixed declared types; retention of conversion results at retrieval; schema API; profile selection method. Preserving all source-ordered occurrences without overwriting is established in [section 9](config-format.md#9-repeated-values-and-read-state), and syntax result and failure contracts are established in [section 11.2](config-format.md#112-syntax-results-and-failure-contracts) |
| Formatter | Whether one will be provided and its formatting policy |

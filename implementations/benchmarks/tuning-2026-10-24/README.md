# Go parser tuning measurements

This published campaign measures changes to the general Go parser and common
string decoder against the baseline identified below. The aim is to reduce
the time and allocation traffic needed to load equivalent settings while retaining the current
[specification](../../../docs/config-format.md), public APIs, output ownership,
source order and diagnostics.

The [benchmark overview](../README.md) links to the latest published results
for each measurement suite. This report covers the decoded common-map comparison
and the Go API stages. The [comparison guide](../comparison/README.md) explains
the equivalent-format method. Native parser and process-memory measurements
have their own output contract and report.

## Findings

The tuned direct loader reduced median load time by **28.8–38.2%** across the
six equivalent-map workloads. Its allocation traffic and allocation counts
also fell in every case. At 512 ASCII settings, the median changed from
162.545 to 109.536 µs, with 153,136 → 120,368 B/op (**21.4% fewer bytes**) and
2,446 → 1,422 allocations (**41.9% fewer allocations**).

The same campaign's JSON medians were 104.660 µs in the baseline binary and
102.335 µs in the tuned binary. The dotReg/JSON median ratio therefore moved
from about 1.553 to 1.070. The tuned time ranges overlap; this is evidence of a
smaller observed gap, rather than a guarantee of equal performance. The tuned
large ASCII load is about 3.0% above JSON's median. Unicode and escaped inputs
have lower dotReg direct medians than the other libraries, by about 10.0% and
5.1% respectively. The Unicode ranges are separated in this campaign, while
the escaped ranges overlap; neither result establishes a universal format
ranking. Multiline remains the largest gap: the tuned direct median is 25.3% above TOML's median.

All 13 parser, decoder and construction stages have lower observed median
times, with no increase in allocation bytes or counts. Plain 32 KiB block
decoding changes from 7.2315 to 0.99165 µs while retaining zero allocations;
this operation validates and decodes an already parsed body. The escaped-body
decoder changes from 50.5425 to 46.4515 µs with its original 113,400 B/op and
19 allocations. The prefix-selection algorithm and its allocation totals are
unchanged; its small timing movements are not presented as a selection
algorithm improvement. Each stage's ranges are retained below.

## Implementation changes

The tuning applies to ordinary parser and decoder operations, without fixture
names, predetermined key counts or a special two-level configuration grammar:

- Build a value entry's final owned path directly. Only headings retain the
  persistent scope nodes needed by later relative keys. Visitor path slices
  remain independent of parser scope storage.
- Use byte operations for ASCII space/tab trimming and the ASCII part of bare
  key validation. Non-ASCII elements retain Unicode whitespace and control
  checks; key identity is not normalised or case-folded.
- Copy unescaped quoted key names and values directly into compact storage.
  A short decoded string therefore cannot retain an unusually long source line
  through an interior substring. This keeps the compact ownership of the
  original decoder while avoiding its builder path for unescaped text.
- For ordinary quoted names and values, calculate the exact decoded UTF-8 size
  while locating the closing quote, then allocate the output once. Escaped
  block bodies retain their single-pass builder rather than paying for a
  separate sizing pass. Both paths use the common escape decoder; independent
  validation of manually constructed `Entry` values remains in `DecodeString`.
- Assemble small pipe bodies using one correctly sized result allocation.
  The temporary buffer holds at most eight physical lines and 4,096 bytes of
  original source, including discarded indentation. Larger bodies flush the
  buffered prefix and continue through the streaming builder with its ordinary
  incremental growth. These are buffering thresholds, not notation length
  limits.

An exploratory candidate also used an extra escape-sizing pass for block
bodies. Separate API measurements showed an escaped-block CPU-time regression,
so that change was rejected before the final candidate was measured. Both final
paired campaigns are rerun in full after this revision; exploratory candidate
observations are not mixed into their results.

The ordered consumer, profile conversion and prefix-selection contracts are
retained. The common-map comparison uses `ParseEach` or `Parse` followed by
`DecodeString` and construction of the application map; it does not time
`Build` or prefix selection. Those operations are assessed separately in the Go
API campaign.

## Paired measurement protocol

Both final campaigns ran on Windows 11 Enterprise 10.0.26200 AMD64 with
Go 1.27.0 and CPython 3.12.14, on an Intel Core i7-1370P (14 cores, 20 logical
processors) with 16,819,617,792 bytes of physical RAM. The
[host observation](host.json) was taken during the final API campaign; the
existing custom power scheme `MY` remained active. This is a timestamped
snapshot, not continuous control of CPU frequency, thermals, battery state or
desktop/OS activity.

Both variants use Go 1.27.0 and test binaries built with `go test -c -trimpath`.
The parser's source changes are the experimental difference. The existing
fixture generator, serialisations, independent expected outputs, comparison
adapters, benchmark loops and library dependencies are frozen across variants.

Each campaign uses ten balanced rounds. A round contains every
`(variant, operation)` pair exactly once. A seed of `20261024`, increased by one
per round, shuffles the complete pair list together. Baseline and candidate are
therefore interleaved throughout the same campaign instead of being measured in
separate before and after blocks. Jobs run serially.

Before measurement, each binary runs one `1x` discovery pass. Their discovered
operation names must match. Each subsequent child process executes exactly one
operation, selected by an anchored expression for every slash-separated name
segment. The time target is `200ms`, with `-test.cpu=1`, `GOMAXPROCS=1`,
`GOGC=100` and `GOMEMLIMIT=off`. The Go benchmark runner performs its normal
calibration and collection between samples; there is no additional forced GC
inside the measured loops. Test setup, fixture generation and independent
output checks remain outside the Go timers.

Every process sample is retained. The controller records its variant, round,
shuffle seed, execution sequence, exact flags, UTC start/end and total process
wall time. It rejects missing or duplicate operations, incomplete sample counts
and inconsistent metric sets. JSON and raw-output writes occur between child
processes, outside all Go operation timers. No outliers are removed.

Each observation starts in a fresh process. Setup and calibration costs remain
visible in process wall times but are excluded from `ns/op`. These short warmed measurements do
not establish a universal steady state. Operating-system scheduling, desktop
activity, clock rates and thermal state can still affect observations; the
jointly shuffled rounds reduce systematic association with one variant.

The comparison preserves the common contract of a fresh
`map[string]map[string]string` containing identical decoded strings. No parser
receives counts from the independent oracle or reuses its prior result. UTF-8,
escaping, multiline spelling, fixture sizes and hashes are those recorded in
the [fixture manifest](../comparison/fixtures-manifest.json). The comparison
includes the unchanged JSON, TOML, YAML and INI operations in both variants;
their observations also show variation within this campaign. Library names,
versions and syntax choices are described in the
[comparison method](../comparison/README.md).

## Reading the results

The recorded median and minimum–maximum range describe each operation's
observations. The controller also records candidate/baseline median ratios.
A ratio below one means a lower value for that metric; ratios between medians
are descriptive and do not establish statistical significance. Small differences
should be assessed against the observed spread and the unchanged operations.

Time per complete load is the primary comparison for equivalent configuration
formats. Values per second and logical UTF-8 bytes per second use the common
decoded payload. Encoded MB/s is diagnostic because the serialisations have
different byte sizes. The Go API benchmarks instead measure the stage identified
by each name; prefix selection starts from an already built `Config` and has no
input-byte throughput claim.

`B/op` and `allocs/op` are Go heap allocation traffic per operation. They are
neither retained memory nor process peak RSS. This campaign does not measure
electricity consumption. The latest published
[native report](../public-rollin-2026-10-24/README.md) contains process-memory
observations for its own recorded source snapshots and native workloads.
Those figures describe a separate measurement contract from these Go API stages.

## Compatibility checks

The final parser passes `go test -count=1 ./...`, `go vet ./...` and
`go build ./...`. Its shared conformance checks compare syntax, decoded values,
errors and physical lines with the independent corpus. Focused regressions
cover visitor-owned paths, multi-element headings, ASCII/Unicode classification,
all pipe-buffer transitions, mixed LF/CRLF, long lines/margins, quoted escape
sizes, surrogate pairs, decode-once behaviour and diagnostic privacy. Those
new regression tests also pass against the unmodified baseline implementation.

The final five-second fuzz campaign completed 8,346 executions without a
failure. The existing CI additionally runs the Go platform/version matrix,
race and fuzz checks, shared CLI conformance and the comparison equivalence
suite. It verifies this report's generated tables against every retained
observation using `render.py --check`; CI has no performance threshold.

## Reproduction from the repository root

Use the recorded Go and CPython versions. The PowerShell example
exports the baseline without changing the candidate checkout, builds both
variants before measurement and writes reports to a fresh temporary directory.
Set `$python` to the appropriate CPython command or executable on the host.
Do not modify sources or run another CPU workload while the campaigns execute.
The complete Git archive includes `conformance/cases.json`, which is required
if the baseline's full Go test suite is also run. An export restricted to parser
and benchmark sources is insufficient for that separate conformance validation.

```powershell
$python = "python"
$candidateRoot = (Get-Location).Path
$baselineCommit = "d825e2aead924671c3fe01ec07d5ad2d6df25bd6"
$campaignId = [guid]::NewGuid().ToString("N")
$baselineRoot = Join-Path $env:TEMP "dotreg-before-$campaignId"
$baselineArchive = "$baselineRoot.zip"
$reportRoot = Join-Path $env:TEMP "dotreg-tuning-$campaignId"
New-Item -ItemType Directory -Path $reportRoot | Out-Null
git archive --format=zip --output=$baselineArchive $baselineCommit
if ($LASTEXITCODE -ne 0) { throw "Baseline export failed" }
Expand-Archive -LiteralPath $baselineArchive -DestinationPath $baselineRoot

foreach ($variant in @("baseline", "candidate")) {
    $variantRoot = if ($variant -eq "baseline") { $baselineRoot } else { $candidateRoot }
    foreach ($suite in @("comparison", "go-api")) {
        $relativeModule = if ($suite -eq "comparison") {
            "implementations/benchmarks/comparison"
        } else {
            "implementations/go"
        }
        Push-Location (Join-Path $variantRoot $relativeModule)
        try {
            $binary = Join-Path $reportRoot "$variant-$suite.test.exe"
            go test -c -trimpath -o $binary .
            if ($LASTEXITCODE -ne 0) { throw "$variant $suite build failed" }
        } finally {
            Pop-Location
        }
    }
}
```

Run the format comparison first, then the API campaign:

```powershell

```

Check that both JSON reports have `"status": "complete"`, and verify their
source/binary manifests before copying the four reports into this directory.

`"status": "running"` and must not be used as the completed result. Use fresh
output paths for each campaign as shown above. The published JSON manifests,
rather than a later checkout's branch name alone, identify the measured
